# TourDesk 0.2 — рабочая кодовая база (Белтуризм)

**Статус:** разработана базовая full-stack версия, но **не размещена в облаке** и **не подключена к вашей базе Supabase**, поскольку проект и ключи не предоставлены. Без них интерфейс показывает вход и предупреждение о необходимости настройки. **Автоматическое изменение данных на живых сайтах требует проверки на реальном сервере и облачной базе.** Адаптер Белтуризм умеет принимать проверенные по структуре строки календаря, но интеграционный прогон на реальном HTML и Supabase пока не выполнен. Такой статус — намеренный, не имитация синхронизации.

Исходный прототип находится в `docs/tourdesk_prototype_v2.html`: сохранены тёмно-синяя навигация, светлая тема, карточки, вкладки трёх способов добавления, возможность нескольких выездов, избранное и генерация сообщений. Хранение теперь **только в PostgreSQL**, а не в `localStorage`. Демо-туры не создаются.

## Архитектура

- **Frontend:** модульный JavaScript, адаптивные HTML/CSS, интерфейс на русском. Без инструментов сборки и внешних UI-пакетов. Отличие от первоначально предложенного Next.js — предельно простой запуск и возможность локальной проверки без npm-зависимостей; при росте проекта фронтенд можно перенести на Next.js, сохранив API и схему базы.
- **API:** Node.js 22+ HTTP-сервер `server/index.mjs`, валидация, защищённые cookie-сессии, серверная обработка ссылок, API для тура, изменений, уведомлений, истории и авторизации.
- **Облачная БД:** PostgreSQL Supabase, RLS и транзакционные RPC-функции. Supabase Auth для email/пароля. Нет локальных копий данных о турах.
- **Синхронизация:** `server/worker.mjs` (отдельный процесс раз в час) или защищённый POST `/api/cron`. Интервалы на уровне тура: 6/24/72 ч или вручную. Данные сайта применяет только защищённая DB-функция `apply_snapshot` после проверки источника.
- **Адаптеры:** реестр `server/adapters/index.mjs`, отдельные адаптеры `belturizm.mjs` для `belturizm.by` (разбор календаря и программы) и `globalTravel.mjs` для `global-travel.by` (в **статусе unverified**). Неуниверсальный адаптер предназначен для доработки по реальным HTML-образцам; пока он не может без проверки перезаписывать цены или расписание. Другие сайты предварительно разбираются по JSON-LD/текстовым правилам, но не синхронизируются автоматически.

## Быстрый запуск

1. Установите Node.js **22 или новее**. Устанавливать npm-пакеты не требуется.
2. Создайте новый проект в [Supabase](https://supabase.com/dashboard).
3. Откройте **SQL Editor** в Supabase и выполните файл `supabase/migrations/001_tourdesk.sql` полностью **один раз**, затем выполните `supabase/migrations/002_belturizm_availability.sql`. Проверяйте сообщения об ошибках, не игнорируйте их.
4. В **Authentication → Providers → Email** разрешите вход по email. Для регистрации можно оставить подтверждение email; после подтверждения пользователь получает свою рабочую область через SQL-триггер. Если аккаунт существовал до миграции, рабочую область нужно создать вручную (см. ниже).
5. Скопируйте `.env.example` в `.env`, заполните `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET` и `APP_ORIGIN`. `SUPABASE_ANON_KEY` — publishable/anon ключ; `SUPABASE_SERVICE_ROLE_KEY` — секретный, только на сервере. **Никогда не публикуйте `.env`, не загружайте его в репозиторий.** Для production требуется HTTPS и соответствующий `APP_ORIGIN`.
6. Выполните в папке TourDesk: `npm start`. Откройте `http://localhost:3000`.
7. Создайте аккаунт, войдите в него, добавьте первый тур вручную. Он сохраняется в Supabase и должен остаться после выхода и повторного входа.
8. Для фоновых проверок запустите **отдельный постоянно работающий процесс**: `npm run worker`. На бесплатном сервере, который засыпает, автоматическая синхронизация не будет выполняться. Альтернатива: cron POST-запрос к `/api/cron` с заголовком `Authorization: Bearer <CRON_SECRET>` раз в час.

### Пример `.env`

```sh
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVER_ONLY_SECRET
CRON_SECRET=PASTE_RANDOM_32+_CHARACTER_VALUE
APP_ORIGIN=http://localhost:3000
PORT=3000
```

В реальном публичном развёртывании замените `APP_ORIGIN` на HTTPS-домен. Добавьте секреты в менеджер окружения хостинга и включите перезапуск процесса после сбоев. Периодически создавайте резервные копии через Supabase Dashboard (доступность функций зависит от тарифа) или отдельный `pg_dump` из защищённого административного окружения. Проверьте восстановление на тестовой БД.

### Аккаунты, существовавшие до миграции

Схема создаёт персональную рабочую область при **новой регистрации**. Если пользователь уже был в Auth, выполните в SQL Editor (заменив email):

```sql
do $$
declare uid uuid; wid uuid;
begin
 select id into uid from auth.users where email='agent@example.com';
 if uid is null then raise exception 'User not found'; end if;
 if not exists(select 1 from public.memberships where user_id=uid) then
   insert into public.workspaces(name) values('Мой TourDesk') returning id into wid;
   insert into public.memberships(workspace_id,user_id,role) values(wid,uid,'owner');
 end if;
end $$;
```

## Как устроена обработка туров

**Ручной ввод.** Название, страна и набор выездов; у каждого дата начала, опционально окончание, цена, валюта и примечание. При сохранении в одной транзакции изменяются тур/выезды и записывается история ручных изменений цен и дат. История не смешивается с текущим значением. Повторяющаяся дата запрещена в рамках одного тура (для двух цен одной даты потребуется отдельная тарифная модель в будущей версии).

**Вставка текста.** Простой детерминированный разбор (`server/parser.mjs`) выделяет некоторые страны, даты, цены, валюты, продолжительность и разделы описания. Результат всегда предварительный, отсутствующие сведения отмечаются. **Это пока не ИИ-анализ:** `OPENAI_API_KEY` зарезервирован в окружении, интеграция с ИИ не реализована.

**Ссылка.** Сервер делает HTTPS-запрос с проверкой публичных IP, ограничением размера и времени и повторной проверкой перенаправлений, извлекает JSON-LD или использует адаптер. Для динамических сайтов (JavaScript-рендеринг) браузерный сбор данных пока не подключён; такие страницы могут вернуть неполный результат. В интерфейсе будет предупреждение.

**Синхронизация.** Для каждого сайта нужен отдельный проверенный адаптер. Успешный парсер возвращает `{ tour, departures, confidence: 'verified', datesComplete: true/false }`. При `confidence !== 'verified'` сервер **не изменит данные**, а зарегистрирует ошибку проверки. При достоверных данных цена изменяется автоматически, история и уведомления добавляются; новые даты добавляются. Отсутствующие даты помечаются `missing` только при достоверно полной выдаче дат и непустом списке; на ошибке запроса — никогда. Текстовые поля попадают в `pending_changes` и требуют подтверждения. `field_rules` позволяет отключить автообновление цен/дат или игнорировать предложения по текстам.

### Как подключить нового туроператора

1. Уточнить официальный API / JSON / XML этого оператора и право на использование данных. Предпочесть структурированный источник.
2. Получить **разрешённые к обработке** реальные образцы нескольких страниц: цены, 2–3 даты, разные валюты, отсутствующая цена, ошибка загрузки, исчезнувшая дата.
3. Создать `server/adapters/<operator>.mjs` с методами `matches(host)` и `extract({ html, url })`; подключить в `server/adapters/index.mjs`. Один адаптер на конкретный сайт.
4. Возвращать `confidence:'verified'` **только** если извлечение надежно проверено на реальных страницах. `datesComplete:true` устанавливать отдельно, только если источник гарантирует полный список выездов, иначе оставлять `false`.
5. Написать тесты на HTML-фикстурах и на прямом ответе реального сайта (с разрешением на запросы). Проверить на тестовом Supabase изменение цены, появление даты, исчезновение даты, восстановление, предложенное текстовое изменение, ошибку HTTP и отсутствие цены. Лишь после этого включать продуктивный worker.
6. Для JavaScript-сайтов создать отдельный серверный браузерный адаптер или интеграцию с API. На этапе `0.1` такого раннера нет.

## Эндпоинты

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | Статус сервера и настройки БД |
| `POST /api/auth/signup`, `/login`, `/logout` | Supabase Auth, HTTP-only cookie |
| `GET /api/me` | Текущий пользователь и рабочая область |
| `GET /api/tours` | Список туров и всех выездов |
| `POST /api/tours` | Транзакционное создание/редактирование через SQL RPC |
| `PATCH /api/tours/:id` | Избранное / отдельные клиентские тексты |
| `DELETE /api/tours/:id` | Удаление с серверным контролем прав |
| `GET /api/tours/:id/history` | История цен и дат |
| `POST /api/parse` | Предпросмотр разбора по ссылке или тексту |
| `POST /api/tours/:id/check` | Ручная проверка источника |
| `GET /api/updates` | Уведомления, предложенные изменения, проверки |
| `PATCH /api/notifications/:id/read` | Прочитано |
| `POST /api/changes/:id/decision` | Принять/отклонить текстовые изменения |
| `POST /api/cron` | Проверка туров, подлежащих синхронизации (только секрет cron) |

Все операции с турами требуют авторизации. RLS разделяет рабочие области, таблицы запрещают прямые неаудируемые изменения, секретный ключ остаётся на сервере. Модель `memberships` предусматривает будущие роли owner/editor/viewer, но интерфейс управления сотрудниками ещё не реализован.

## Что работает в коде, а что ещё требует интеграции

| Функция | Статус |
|---|---|
| Интерфейс, адаптивная навигация, карточки и четыре даты с раскрытием | Реализовано |
| Ручной CRUD, страны, избранное, поиск, фильтры | Реализовано, требует подключения БД для сквозной проверки |
| Отдельные цены и валюты по датам; серверная история | Реализовано в коде / SQL, не проверено на реальном Supabase |
| Краткий / подробный текст, ручные изменения и копирование | Реализовано |
| Supabase Auth и разграничение данных через RLS | Реализовано в коде / SQL, требуется настройка проекта |
| Простейший разбор текста, JSON-LD и статического HTML по URL | Реализовано с обязательной ручной проверкой |
| Полноценный ИИ-разбор сайта и браузер динамических сайтов | **Не реализовано** |
| Надёжный живой адаптер туроператора с автоматическим применением цен и дат | **Не подключён и не проверен**; пилот Global Travel в режиме без изменений |
| Транзакционная sync-логика, хранение истории, пропавшие даты и подтверждение текстов | Реализовано в SQL, требует интеграционного теста на облачной БД |
| Автоматическая проверка по расписанию | Код worker/cron есть; требуется хостинг, ключ и проверенный адаптер |
| Управление сотрудниками, разрешения на уровне карточек, импорт прошлой localStorage-базы | **Не реализовано** |
| Резервное копирование по расписанию | **Не реализовано внутри приложения**; предлагается штатный PostgreSQL backup |
| Проверка на реальных 10–20 сайтах и на мобильном браузере | **Не выполнена** |

## Проверки

Команда: `npm test`. Выполняются чистые тесты разбора текста, всех дат, валют, истории изменений на уровне доменной логики, запрета ложного удаления, восстановления даты, SSRF-защиты, валидации и HTTP-проверка доступности статических файлов. **Это не сквозной тест SQL на Supabase.** Для запуска в боевую эксплуатацию обязательно проверить миграцию, RLS, реальный CRUD и каждую операцию синхронизации на выделенной тестовой базе.

Сохранён оригинальный прототип — его можно открыть для визуального сравнения и переноса ранее введённых данных **вручную**. Прямая миграция данных из его `localStorage` отсутствует.


## TourDesk 0.2: пилот Белтуризм

Тестовая ссылка: `https://belturizm.by/trip/tur-v-parizh-bez-nochnykh-pereezdov/`.

Добавлен **специализированный** адаптер `server/adapters/belturizm.mjs`. Он ищет строки календаря, в которых явно есть две даты, отдельная цена, валюта и отметка доступности. При неполных строках весь снимок получает `needs_review`, и автоматическое обновление не производится. Проверено на тестовом HTML-фрагменте, **воспроизводящем видимое содержимое страницы по состоянию на 04.11.2026**, а не на скачанном реальном HTML-коде (прямая сеть недоступна в среде подготовки). Сайт может менять верстку, поэтому обязательна интеграционная проверка на рабочем сервере до включения фоновых проверок.

**Ключевые особенности источника:**

- Календарь может быть частичным: есть «More Dates». `datesComplete` всегда `false`. Отсутствующие в ответе даты **не** считаются снятыми с продажи. Позднее можно исследовать документированный API/механизм подгрузки всех дат и только после строгой проверки разрешить полное расписание.
- Выбранная валюта отображения может меняться (страницы наблюдались в EUR, USD и BYN). Если для существующего выезда меняется валюта, автоматическое обновление отменяется до ручной сверки. Это защищает от ложного изменения цен из-за конвертации.
- Каждая видимая строка содержит индивидуальную цену и доступность. Расширение БД `002_belturizm_availability.sql` добавляет `departures.availability` (`available`, `sold_out`, `unknown`), историю изменения доступности и уведомления. В каталог и подробную карточку добавлены статусы «Есть места» и «Мест нет».
- На проверяемой странице рекламный текст указывает другую минимальную цену и «выезды по воскресеньям», хотя календарь содержит другие цены и субботние отправления. Эти фразы не включаются в краткий текст автоматически; оригинал сохранён во внутренней заметке, а конфликт — в предупреждении предварительного просмотра.
- В `examples/belturizm_paris_preview_2026-11-04.json` лежит пример предварительного разбора по тестовой странице. **Это не импортированная карточка в облачной базе и не результат прямого вызова `/api/parse` на действующем сервере.** Данные требуют повторной проверки при бронировании.

### Как запустить проверку именно этого источника

1. Для новой установки выполните обе миграции SQL по порядку. Для старой базы с уже выполненной миграцией 001 — **только миграцию 002**. Обязательно сохраните резервную копию до обновления.
2. Настройте Supabase, выполните `npm start` и откройте TourDesk.
3. В разделе «Добавить тур» вставьте ссылку и нажмите «Разобрать тур». Проверьте даты, валюту, поля, предупреждения, сохраните.
4. На тестовой Supabase измените исходную цену **в тестовой копии данных или контролируемом ответе** и запустите «Проверить сейчас». Проверьте `price_history`, `departure_events`, уведомления и корректность полей после повторного входа.
5. Только после успешных сквозных проверок на реальном HTML и БД включите синхронизацию по расписанию.

**Пока не реализовано:** получение всех дат за кнопкой «More Dates», прямой интеграционный тест живого сайта на нашем сервере, тест транзакций на подключённом Supabase и облачный деплой. Поэтому нельзя считать синхронизацию в production доказанно работающей.
